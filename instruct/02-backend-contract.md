# 02 — Backend contract

## Goal

Define the HTTP contract this app expects from the backend service for register, confirm and resend. **This is the proposed contract; the backend adapts to it.** If the backend team changes anything, change it *here first* — `03`, `04`, `05` and `07` all read from these tables.

## Read first

- `node_modules/next/dist/docs/01-app/02-guides/backend-for-frontend.md` ("Proxying to a backend", "Security")

## Conventions

- Base URL: `BACKEND_API_URL` (server-only env). All paths below are relative to it.
- JSON in, JSON out. `Content-Type: application/json; charset=utf-8`.
- Every request carries `X-Request-Id` (UUID v4, generated by the Server Action). The backend echoes it in the error envelope and in its own logs.
- If `BACKEND_API_KEY` is set, every request carries `Authorization: Bearer <key>`. This is service-to-service auth, not user auth.
- Timeout budget: the app aborts after `REQUEST_TIMEOUT_MS` (default 5000). Email sending must be async on the backend side so register returns well under that.
- The backend is the **authoritative** rate limiter. The app adds a light limiter as defense in depth (`03`).

## Error envelope (all non-2xx)

```json
{ "code": "EMAIL_TAKEN", "message": "human readable, not shown to users", "requestId": "…" }
```

`code` is an upper-snake string from the tables below. `message` is for logs. The app never displays `message`; it maps `code` to its own copy.

Any non-2xx response that is *not* this shape, or any network failure/timeout, is treated as `UPSTREAM` and shown to the user as a generic failure with a reference id.

## Endpoints

### `POST /auth/register`

Creates an unconfirmed account and sends the confirmation email.

Request:

```json
{ "email": "ren@example.com", "password": "correct horse battery", "displayName": "Ren" }
```

Headers: `Idempotency-Key: <uuid>` — the app generates one per rendered form. Replaying the same key with the same body must return the original response instead of creating a second account or sending a second email.

| Status | `code` | Meaning | App behavior |
|---|---|---|---|
| 201 | — | `{ "userId": "usr_…" }` | Redirect to `/register/check-email` |
| 409 | `EMAIL_TAKEN` | An account with this email exists (confirmed or not) | Field error on email with a link to sign in (stub) |
| 422 | `VALIDATION` | Backend-side validation failed. Body may include `"fields": { "email": ["…"] }` | Map to field errors; fall back to form error |
| 429 | `RATE_LIMITED` | Too many attempts | Form error "Too many attempts…" |

Validation the backend must enforce (the app enforces the same before calling):

- `email`: RFC 5322 shape, ≤ 254 chars, stored lowercase.
- `password`: 10–128 characters, any characters, no composition rules (NIST 800-63B). Recommended: reject passwords found in a breach corpus; return `422 VALIDATION` with `fields.password`.
- `displayName`: 2–40 characters after trimming.

Enumeration note: `409` reveals that an email is registered. For a social app whose sign-up already reveals this via the login page, this is acceptable. If the backend team prefers zero enumeration, return `201` for taken emails too and send an "you already have an account" email; the app handles that with no change.

### `POST /auth/confirm-email`

Consumes a confirmation token.

Request:

```json
{ "token": "<opaque url-safe token>" }
```

| Status | `code` | Meaning | App behavior |
|---|---|---|---|
| 200 | — | `{ "status": "confirmed" }` | Show confirmed state |
| 200 | — | `{ "status": "already_confirmed" }` | Show already-confirmed state |
| 400 | `TOKEN_INVALID` | Unknown, malformed, or already-consumed token | Show invalid state with resend |
| 410 | `TOKEN_EXPIRED` | Known token past its TTL | Show expired state with resend |
| 429 | `RATE_LIMITED` | | Form error |

Must be idempotent: confirming an already-confirmed account returns `200 already_confirmed`, never an error.

### `POST /auth/resend-confirmation`

Request:

```json
{ "email": "ren@example.com" }
```

| Status | `code` | Meaning | App behavior |
|---|---|---|---|
| 202 | — | Accepted — **returned whether or not the email exists or is already confirmed** | Show "If an account exists for that email, a new link is on its way." |
| 429 | `RATE_LIMITED` | | Form error |

Backend rate limit recommendation: 3 per email per 15 minutes, 10 per IP per hour. Invalidate previous tokens when a new one is issued.

## Token specification

- ≥ 32 bytes of CSPRNG output, base64url-encoded without padding → 43+ characters matching `^[A-Za-z0-9_-]{43,256}$`. The app rejects anything else *before* calling the backend.
- Single use. TTL 24 hours.
- Store only a hash of the token; never log the raw value. The app never logs it either.

## Confirmation email

The backend sends the email. The link must point at **this app**, not the backend:

```text
${APP_URL}/confirm-email?token=<token>
```

`APP_URL` is the public origin of this Next.js deployment (the backend needs its own copy of that value). The page does not consume the token on load — the user clicks "Confirm email". Scanners that prefetch the link therefore do not burn it. Do not add any "auto-confirm on GET" endpoint on the backend side.

Email copy is owned by the backend team, but should use the same verbs as the app: subject "Confirm your email for Lively", button "Confirm email".

## Checklist for the backend team

- [ ] `X-Request-Id` accepted and echoed in error envelopes and logs
- [ ] `Idempotency-Key` honoured on `/auth/register`
- [ ] Error envelope `{code, message, requestId}` on every non-2xx
- [ ] `/auth/confirm-email` idempotent, distinguishes `TOKEN_EXPIRED` vs `TOKEN_INVALID`
- [ ] `/auth/resend-confirmation` returns `202` unconditionally (except 429)
- [ ] Token: 32-byte CSPRNG, base64url, hashed at rest, 24 h TTL, single use
- [ ] Email link uses `${APP_URL}/confirm-email?token=…`
- [ ] Register responds < 2 s p95 (email sending is queued, not awaited)
- [ ] Rate limits on all three endpoints
